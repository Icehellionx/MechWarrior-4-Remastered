# Cursor clip ownership smoke

Run `dotnet run --project tools/compatibility/CursorClipGuardSmoke/CursorClipGuardSmoke.csproj --configuration Release` on an interactive Windows desktop with no active game. The test first opens a temporary borderless window six pixels wider and 29 pixels taller than the monitor, matching the measured outer oversize in issue #7. It then opens a framed window with a monitor-sized client and a naturally larger outer rectangle. Each case sets a tighter cursor clip as dgVoodoo might, starts the production `SystemGameWindowLifecycleGuard`, and checks that the **client** fits the monitor while active monitoring and guard disposal leave the wrapper clip intact. The framed outer rectangle must remain larger than the monitor. The test restores the clip observed before it in `finally` and writes a timestamped pass/fail result to `%TEMP%\MW4-CursorClipGuardSmoke-result.txt` for desktop launches that lack a console.

This tests Win32 window geometry and cursor ownership, not MW4 mission input, dgVoodoo final scaling, or DPI behavior. A failure to make the synthetic window foreground is inconclusive and must not be reported as a gameplay failure. The source fix follows [Microsoft's shared `ClipCursor` contract](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-clipcursor); it does not copy a third-party input hook.
